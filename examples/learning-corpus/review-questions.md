## 人工审批与状态检查

以下检查面向实际服务，不由上表的知识问答接口代替。准备新的未处理文档与正确的 tenant / actor；不要在已有数据中删除 chunks 来伪造异常。

| 编号 | 操作场景 | 应观察的证据 |
| --- | --- | --- |
| H01 | 新文档仅上传，然后创建允许提议处理的诊断 run | run / tool observation 显示真实文档状态；只有成功创建待审批提议才出现 WAITING_APPROVAL |
| H02 | 暂不批准 CHUNK | 文档不应因为模型提议就自动产生 chunks；保存 pendingApproval 与事件记录 |
| H03 | 批准对应的 CHUNK | actionResults 与 ingestion job 显示真实结果；后续缺失 embedding 可形成独立审批 |
| H04 | 拒绝一次待审批操作（使用独立新 run） | 记录实际拒绝状态与后续 run 结果，确认被拒操作没有执行；不预设终态文案 |
| H05 | 批准 EMBED_MISSING | 检查真实 embeddedChildChunks / childChunks 与任务状态，不只看 worker 日志 |
| H06 | 已完成文档重新做只读诊断 | 不应仅为了演示再次破坏已完成数据；是否无操作以服务的实际诊断为准 |

`scripted` 模式是确定性演示，按 Harness 文档使用相应请求；`pi` 模式中模型决定是否调用提议工具，但 Java 仍负责接受或拒绝提议。不要期待同一句自然语言在不同模型运行中形成完全相同的工具序列。

## 权限与缓存检查

先在 tenant `demo-lab-a`、actor `demo-reader-a` 下以 PRIVATE 上传数据标准。不要在其他公共文档或第二个租户中复制其合成隔离标记，否则会污染测试判断。

1. 所有者按该文件 documentId 检查可访问性，并发起查询。检查能否定位证据，不把未召回直接归因于权限错误。
2. 同租户另一 actor 执行相同访问与查询；其他 tenant 再执行一次。都不应获取该文件的受限正文、引用或缓存上下文。
3. 先让所有者查询以覆盖潜在缓存命中，再执行其他身份查询，检查引用中的 documentId 和上下文，不仅检查自然语言答案。
4. 文件不可访问时，接口可能按既有约定返回 404；断言是“不泄露内容”，不要强制把所有拒绝写成 403。

检索没命中不是隔离已经得到证明。应结合接口权限测试、上下文检查与已有自动化测试，而不是仅凭一次空答案宣布安全。

## 记录格式与限制

每次保留：题号、执行模式、tenant / actor、documentIds、traceId / runId、实际响应、支持段落、通过或失败及原因。不要记录 API key、worker 凭证或真实敏感内容。

把“候选未召回”“上下文裁剪丢失条件”“答案误解版本”“引用不支持结论”“权限泄露”分开记录，避免都归为模型不好。可以用于以后扩展评测，但当前没有运行自动评分，也没有给出 Recall@K、MRR、nDCG 或任何性能分数。
